## 阻塞、前台等待与后台工作不是一回事

- **主线程工作**：分支复制/选择、搜索文本提取、postMessage 同步提交、grep/expand 的同步搜索/格式化。可能影响 Pi 主循环响应；有明确阶段计时，但不是所有同步 SDK 内部操作都有独立探针。
- **前台等待**：用户还拿不到下一步答案，例如等模型、等 worker 准备好、等工具完成。等待期间主循环可能仍能响应，不能直接叫“主线程阻塞”。
- **后台 worker**：分词、索引、候选搜索、去重、排序、分页渲染在独立线程中执行。它仍耗 CPU/内存，且数据提取/传输留在主线程；如果当前查询等它完成，就影响用户等待。

后台索引组：准备好索引的墙钟中位数 **1.78s**；前台索引等待区间并集中位数 **1.74s**；两者重叠 **1.74s**。本次会话一启动就提问，几乎没有闲置预热时间，因此不能把后台构建标成“不影响用户”。两段时间不能相加。

整段 Pi 进程观测的最大事件循环延迟，逐题最大值的中位数为 native437.8ms、grep383.6ms、indexed415.5ms。这不是索引单项 CPU 耗时，也不是“总阻塞时间”：SDK 序列化、GC、调度/资源竞争等可能参与，未做根因拆分。不要把之前孤立索引实验的低延迟当成本次整个 Pi 的低延迟。

worker 子阶段的原始共享计时器曾把同步执行标成 main_thread；导出的 workerStages 已明确归一为 `thread: worker / execution: worker_thread`，保留 rawExecution 供审计。它们不是 Pi 主线程阻塞。后续计时器已修正原始标签。

## 压缩与启动

40 次压缩 RPC 墙钟：中位46.72s、p95112.24s、最大138.53s；累计2115.07s是并行任务的时间之和，**不是整场实际等待时长**。RPC 就绪握手中位606.0ms；从发 compact 到匹配响应的中位46.19s。

原生压缩可能内部进行多次模型请求，但本次扩展钩子不提供这些内部请求的流事件，内部首 token/请求数留空。可测的是 RPC 总时长、就绪、heartbeat、报告的 usage。答题阶段所有尝试共观测61次 provider-prepared 回调；它也不是精确 HTTP 请求计数（连接重试/压缩内部请求未完整计数）。

安全估算器的文件读取、JSON解析、上下文构造和估算各自有计时；这是独立预检进程，**不能冒充 Pi 内部会话加载的拆分**。Pi 内部加载只被包含在启动/就绪边界中，精确分项未知。

## 触发器与覆盖范围

8 个索引会话实际解析到的配置全部为10个用户周期 OR10个工具批次。本次实际触发均为 session_start 预热：历史按文件分段喂入，不等价于现场进行数千次用户对话；也没有把历史消息数算作实时触发计数。

当前自动化离线回归覆盖10/10或自定义阈值、任一触发同时清零两计数器、排队期间新活动不丢失、并行工具一批算一轮、失败/中断、会话切换、后台 live 预索引不改变 eligible DF/N、增量激活、结果完全一致。未观测到的实时增量/周期触发耗时留空，不把离线数据混入本次付费跑分。
